One XHTML file, in place of Markdown.

SemText is a semantic text format: a single XHTML file that a language model reads and writes the way it reads and writes Markdown today. The difference is what the text can say. A fact, a step, a caveat, an incorrect statement, a term and its definition are each written as what they are — a class and a few attributes on a plain element — so the structure is in the text itself, not inferred from it.

Read it as-is. A model, a diff, a terminal, or a person with the file open in an editor sees readable text in document order, with every qualifier spelled out next to the thing it qualifies. Nothing has to run first.

Open it in a browser and the same markup becomes working web components: flashcards flip, quizzes score, tabs switch, code copies, terms preview, and a reader bar tracks the outline. That works in any current browser from a double-clicked file, and none of it changes the text the model wrote.

Why this exists

One file, read as text, as structure, and as a page.

Markdown carries prose well and rich content poorly: it has no place to mark a conclusion as distinct from a decoy, a step as blocked, or a term as defined, so rich content ends up as a page for people plus a separate structured copy for tooling, and the two drift. SemText keeps one file. It stays XHTML, so a browser already knows how to display it and web components can enhance it in place, and it stays text, so a model can read and write it directly with no conversion step in either direction.

Pick a reader to see what each one gets from the same file.

The theme CSS styles the vocabulary directly, so a document is readable the moment it opens. Flashcards flip, quizzes score, tabs switch and disclosures expand — driven by roughly 7 KB of vanilla JavaScript with no dependencies and no network calls.

The same file read as XHTML. Attributes qualify every datum: data-kind says what a thing is, data-status says where it stands, .sem-conclusion and .incorrect-statement distinguish an answer from a decoy. A model does not have to infer the structure, because the structure is written down.

The file opened in an editor, a diff, or a terminal is readable as it is: prose in document order, each qualifier written beside the thing it qualifies, no generated markup to skip past. A model writes the same text back. When a condensed record view is useful, an optional script derives one from the markup, but nothing depends on it.

Degradation

Two states, and the bottom one is the contract.

Every hide rule in the vocabulary CSS is gated on one enhancement marker, data-sem-upgraded, that only a script sets. With no script, nothing is hidden and the document reads as prose. The script adds behaviour without moving content.

State 1 — CSS only
Two stylesheets render every element readably. Quiz answers, collapsed notes and inactive views all stay on the page, because the rules that would hide them never match.
State 2 — the one bundle
semtext.js carries everything scripted: the Lit components, the vanilla handlers for the elements no component defines, and extraction. No dependencies, no network beyond the one file. It is the tier a file you email still has.

The notes further down this page are <sem-note> custom elements; the deck above is wired by the same bundle's vanilla handlers.

Reading

Long-form documents, with the reading affordances left in.

The recall elements above are one use. Most documents are read, not drilled, so the vocabulary also carries what a long document needs: a glossary whose terms preview on hover, references with backlinks, a dated chronology, listings with provenance, notes that sit in the margin, content addressed to a named audience, and links that reach into closed disclosures. Every example in this section is live. So is the bar at the top of this page: a sem-reader, described under Reader below.

This note is data-view-as="margin". On a wide viewport CSS floats it into the right gutter; on a phone it reads inline. Extraction reports the same sem-note record either way.

Glossary

A sem-properties block with data-view-as="glossary". Each property carries an id; a term in prose is a plain anchor to it. The reading bundle gives the anchor a preview on hover or focus (role="tooltip", Esc closes) and the anchor still navigates. With scripts off the link simply jumps to the definition.

One entry in the array extraction returns: a type, an id, qualifiers, a payload of fields and a one-line text.
Which state the document is in: unscripted (CSS only) or driven by the one bundle.
The data-sem-upgraded attribute the script sets on what it wired (and on <html>); every hide rule is gated on it.

Because every hide rule is gated on a tier marker, a document with no script hides nothing, and the records a machine reads are the same at every tier[1].

Chronology

sem-chronology is CSS only: a role="list" of sem-event items in chronological order, each with data-when (and optionally data-until and a data-status from the same vocabulary as sem-step). The visible date is an authored <time>; without one, CSS renders the attribute. Extraction gives each event a positional ordinal.

Code

sem-code wraps one <pre><code> and carries what the listing cannot: a filename, a language and a set of marked lines. The chrome (copy, wrap, a role="status" region) is added by the bundle; the listing text stays byte-identical, and extraction reports it verbatim rather than whitespace-collapsed.

Audience

A sem-audiences block declares the profiles a document knows; any element may carry data-audience. The active profile comes from the sem-audience hash parameter, so a link is a picker. The script sets native hidden on what is not for the reader; nothing is removed, and extraction never looks at hidden, so a filtered document still extracts whole.

Deep links, print, motion

A #id hash resolves through disclosure state: the script opens the enclosing reveal, note, view or flashcard and marks the target for a moment. This link opens a collapsed question further down the page. On beforeprint every reveal is opened and the chrome is hidden by the print stylesheet, so the paper copy is complete; prefers-reduced-motion drops the transitions and smooth scrolling. None of this needs page-specific code.

Reader

sem-reader is the bar pinned to the top of this page: one per document, first child of the wrapper, mints nothing. Its outline is generated from the h2 headings (an authored <nav aria-label="Contents"> child is used verbatim instead), and aria-current="location" follows the heading in view. Focus, type size, face and colour scheme are attributes on <html> that the vocabulary CSS keys on, remembered in localStorage when the browser allows it and forgotten without complaint when it does not. The audience select writes the same hash parameter the picker links above do. None of it binds a global key; Esc closes the outline only while focus is inside it.

Tables

sem-table wraps an authored <table> and adds sort and filter; there is no JSON payload, the markup is the data. Sorting reorders the rows in the DOM, which is the one place the vocabulary moves authored nodes: every row is stamped data-sem-source-index before the first sort, and extraction reads rows back in that order, so a sorted, filtered table extracts exactly as it was written. A numeric cell carries data-value when its text is not the key.

Source

sem-source wraps a section and lets the reader flip it between the rendered result and the markup that produced it. The script copies each wrapper's children into an inert text/plain script before any other handler runs, so the fence shows the section as parsed, before any chrome went in; the bundle renders that copy through a sem-code (copy, wrap) on the first switch. The wrapper mints nothing and its children extract as if it were absent.

Markdown

sem-md holds Markdown as its text and renders it in the browser; tables are the case it exists for. The renderer is a small recursive-descent parser that builds nodes with createElement and textContent, so markup inside the Markdown arrives as characters rather than elements, and a link with a javascript: URL loses its href. The normalised source is kept in a sem-code fence behind the toggle, and that fence is what extraction reads back as the record. It ships inside the one bundle (v0.6): every document carries the parser, so a page can add Markdown without a second script.

References

sem-references numbers its entries with a CSS counter in every tier. Citations in prose are plain anchors; the bundle adds a preview on each, a backlink per citation on each entry, and an external link where an entry has an href. In print the href is written out inside the block, never at the citation[2].

The central invariant: extraction output is identical whether or not JS ran, under any view, and after any interaction.

Quick start

What you actually write.

A SemText document is an HTML file. The vocabulary is custom elements with plain attributes — <sem-facts view-as="flashcards">, <sem-step status="done"> — so any editor, template language or generator that emits HTML can emit it, and the browser parses it with or without a script. 

<!doctype html>
<html lang="en" data-sem-theme="minimal-tech-light">
<head>
  <meta charset="utf-8">
  <title>Auth notes</title>
  <link rel="stylesheet" href="semtext/semtext.css">
  <link rel="stylesheet" href="semtext/themes/semtext-theme-minimal-tech-light.css">
  <script defer src="semtext/semtext.js"></script>
</head>
<body>
<sem-enhanced-document>

  <h1>Auth notes</h1>

  <sem-note variant="warning">
    Refresh tokens rotate per use — each exchange retires the last one.
  </sem-note>

  <sem-facts view-as="flashcards">
    <sem-fact id="f-jwt" kind="concept">
      <statement>JWTs rotate per session</statement>
      <conclusion>Short-lived access tokens; the refresh grant issues a new pair.</conclusion>
      <incorrect-statement>Store the token in localStorage for durability.</incorrect-statement>
    </sem-fact>
  </sem-facts>

</sem-enhanced-document>
</body>
</html>

Save it, double-click it. That is the whole workflow. Written the older way — <div class="sem-note" data-variant="warning"> — it renders and extracts the same; that spelling is the compatibility alias, documented once in the spec's Appendix A.

Adding it to a project

Copy semtext.css and one theme file (themes/semtext-theme-<name>.css) next to your document, and set data-sem-theme on <html> to that theme's name. Add semtext.js, deferred. Paste it inline for a document you intend to send as a single file. Write the content with sem-* elements where interactivity or machine-readability pays. Ordinary HTML stays ordinary HTML. Optional: call SemText.extractRecords where a tool needs the records — extraction ships in the same bundle.

The vocabulary

Twenty-one element types mint records: sem-agent, sem-note, sem-facts and sem-fact, sem-details and sem-detail, sem-procedure and sem-step, sem-properties and sem-property, sem-views and sem-view, sem-reveal, sem-progress, sem-chronology and sem-event, sem-code, sem-references and sem-reference, sem-table and sem-md. sem-reader is chrome and mints nothing. This page mints records for eighteen of them; the three it leaves out are sem-details, sem-detail and sem-progress, because nothing here is an occlusion exercise and there is no honest number to meter.

Scope

What it is not.

SemText is a markup vocabulary and three small scripts. It is not a CMS, a site generator or an application framework, and it has no opinion about how you produce the HTML.
The spec is a draft at . The class-based vocabulary is the current baseline and the custom-element form is arriving alongside it, so element names and attributes can still change. Pin a version.
There is no React in the dependency tree and there is not going to be one. Lit 3 is the only runtime dependency, and it is optional — the vanilla handlers have none.

Reasonable questions

Markdown has nowhere to put the attributes that make a datum machine-readable — no way to mark a conclusion as distinct from a decoy, or a step as blocked. An authoring aid that compiles Markdown into SemText is a reasonable thing to build, but the canonical artifact stays XHTML, because that is the artifact all three readers consume.
A model can read any HTML. What it cannot do reliably is tell a conclusion from a distractor, or a caveat from a heading, when nothing in the markup says so. The claim here is narrow: the attributes remove that guesswork, and the extraction contract makes the result stable enough to cite.
Not yet. This is a draft spec, a reference implementation and a Cypress suite. There are no users to point at, no benchmarks to quote and no production deployments beyond this page and its demos.
