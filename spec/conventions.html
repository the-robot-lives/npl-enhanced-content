SemText -- Format Spec & Conventions

DRAFT v0.7 -- tag form canonical -- this page is written in the format it specifies. v0.7 renames the fact child <sem-distractor> to <incorrect-statement> (breaking; no backward-compatible alias). Normative source: spec/conventions.md[1]; where the two diverge, the Markdown wins.

SemText is an XHTML vocabulary of custom elements: <sem-enhanced-document>, <sem-note variant="tip">, <sem-facts view-as="quiz">, <sem-fact> with <statement> and <conclusion>, <sem-step status="done">, <sem-property key="…">. Element names say what content is; attributes are attributes (view-as, status, key, kind, tags, controls), never data-*. That is the form every example in this spec, the schemas and the reference documents use, and the form every consumer -- theme CSS, the one script, extraction and the JS-off artifact -- accepts as its first-class input.

The v0.4 baseline rendered the same vocabulary as classes on plain elements with data-* parameters. That spelling is retained as a compatibility alias: the mechanical mapping is in Appendix A, the script and the CSS keep accepting it, and a document may mix the two forms. New documents and new tooling write the tag form.

Every vocabulary element on this page is live and written as a tag. Each entry in §5 sits inside a sem-source wrapper: press Source to see the markup exactly as it was written here -- bare attributes, no data-*, no classes.

CSS and script layering, in both distribution forms (§7): (1) the base stylesheet semtext.css (the vocabulary, offline-safe) and the theme file -- --sem-* tokens on [data-sem-theme]; (2) semtext.js -- the one script, a Lit 3 bundle that also carries the vanilla handlers for the elements no component defines, the reading and Markdown renderers, and extraction. The single-file form inlines all of it in <head> (the build's sem:inline markers); the folder form links the same files by relative path. Neither form carries page-local CSS or JS beyond a small layout layer. A document without the script shows its authored text -- not styled, not interactive (§4). ? = open questions (§10).

This page ships the folder form: two theme stylesheets, the vocabulary stylesheet, one layout stylesheet and the one bundle linked from <head>, no inline CSS or JS. Its scripts-stripped twin, conventions.nojs.html, is the JS-off proof.

0. Model

One file, three consumers. Element names are semantic (sem-fact, sem-detail) -- what content is; presentation is parameterized (view-as="quiz|flashcards|list") -- how it renders. NPL conventions live inside the tags, never as a pre-HTML grammar.

Double-click, styled, interactive. The theme CSS renders the vocabulary; the script adds the behaviour.

The same XHTML read structurally; attributes qualify every datum; the same XML vocabulary NPL's MCP server already speaks.

Browser render or DOM-text extraction; the content is complete without JS.

A SemText element is a custom element in the sem- namespace. Custom elements are valid HTML whether or not a script ever defines them: the browser parses <sem-fact> as an unknown element, the vocabulary CSS gives it a block box (sem-*:not(:defined) base, §6), and semtext.js -- when it runs -- defines the interactive ones and upgrades them in place (§4 rule 2). Without it the document is plain text in flow.

1. Document skeleton

<!doctype html>
<html lang="en" data-sem-theme="minimal-tech-light">
<head>
  <meta charset="utf-8">
  <title>Authoring Guide</title>
  <link rel="stylesheet" href="semtext/semtext.css">
  <link rel="stylesheet" href="semtext/themes/semtext-theme-minimal-tech-light.css">
  <script defer src="semtext/semtext.js"></script>  <!-- the one script (§4) -->
</head>
<body>
<sem-enhanced-document>

  <sem-reader controls="outline,progress,focus,type,color,print,audience"></sem-reader>

  <!-- document-level metadata: bare semantic children -->
  <agent>
    <name>Infra Guide</name>
    <bio>Deployment runbook assistant</bio>
    <instructions>Answer from sem-fact ids only.</instructions>
  </agent>

  <h1 data-kind="title">Authoring Guide</h1>

  <sem-note variant="warning">Rotation is <strong>per session</strong>.</sem-note>

  <sem-facts view-as="flashcards">
    <sem-fact id="f-jwt" kind="concept">
      <statement>JWTs rotate per session</statement>
      <conclusion>Short-lived access; the refresh grant issues a new pair.</conclusion>
    </sem-fact>
  </sem-facts>

  <!-- content: sem-* vocabulary + ordinary semantic HTML -->

</sem-enhanced-document>
</body>
</html>
  • <sem-enhanced-document> is the required root wrapper (the script scopes to it). It may carry a landmark role (role="main") -- it is the document. The alias form may put the sem-enhanced-document class on a <main> element for the native landmark; the tag form trades that for one element that is the same in every consumer, and states the landmark with role.
  • <sem-reader>, when used, is the wrapper's first child (one per document; §5).
  • Metadata children (agent, and future org, context, audience) are bare semantic tags -- machine-facing, unstyled.
  • Record parts are bare semantic children too: <statement>, <conclusion>, <incorrect-statement> inside sem-fact; <highlight> inside any prose element; <name>, <bio>, <instructions> inside agent.
  • Ordinary semantic HTML is always valid content; sem-* enhances where interactivity pays. Plain HTML carrying data-kind or data-tags is a record too (extraction §3) -- on a standard element the qualifier keeps the data-* spelling, which is the only valid custom attribute HTML5 allows there (§2).

2. Attribute catalog

Global attributes (any sem-* element), spelled bare:

| Attribute | Values | Machine meaning | | :-- | :-- | :-- | | `kind` | free token (`concept`, `anti-pattern`, `caveat`, ...) | what the data IS | | `tags` | comma list | classification | | `view-as` | element-defined modes | presentation parameter (identity unchanged) | | `status` | `done`, `current`, `todo`, `blocked`, `pass`, `fail` | lifecycle/verdict | | `controls` | comma flags: `shuffle`, `filter`, `retry`, `picker` | which controls render | | `collapsed` | boolean | pre-collapse state | | `audience` | profile spec: `a`, `a, b`, `!a` (profiles from `sem-audiences`) | who the datum is for -- **`spec/schema/sem-audiences.md`**; carried verbatim by extraction, never suppresses a record | | `id` | doc-unique | stable anchor, cite target -- a `#id` or `#container/child` hash reaches it through any closed reveal, collapsed note, inactive view or non-current card (deep-link resolver) | | `data-*` | free | extension point; also the **alias spelling** of every parameter above (Appendix A) |

Element-specific parameters (variant, key, name, summary, value, label, when, until, lang, filename, mark, wrap, href, cite, implies, sticky, outline-depth) follow the same rule: bare on the element, documented per schema.

Scope of the bare spelling. Bare attributes are canonical on sem-* custom elements and their bare part children (<statement>, <highlight>, <agent> › <name>), where any attribute name is valid. On a standard HTML element (<h2>, <p>, <a>, <td>) a global qualifier keeps the data-* spelling -- <h2 data-kind="section" data-tags="auth">, <p data-audience="operator">, <td data-value="900"> -- because HTML5 allows no other custom attribute there and §8 promises tool-parseable documents. The script reads both spellings on either kind of element.

view-as is the core inversion: <sem-fact> is a fact in every view; view-as only selects rendering. Unknown view-as ⇒ falls back to list/plain + a console warning. CSS-only modes exist too: sem-note view-as="margin" (right-gutter aside on wide viewports), sem-chronology view-as="timeline|list". sem-properties view-as="glossary" adds term previews from the script.

data-<name> is accepted everywhere <name> is, and wins when both are present (extraction §3.6; the script copies each bare parameter to its data-* twin before any handler runs, §4 rule 1). Writing both spellings on one element is an authoring error -- the precedence exists so extraction stays stable and the mirror is a no-op, not so an author can mean two things; a sem-source fence always shows the markup as authored, so a mixed element would display a parameter the script does not use. State the script writes is always data-* -- data-active on the shown view, data-view-as rewritten by a sem-source / sem-md toggle, the data-sem-upgraded marker -- so an authored bare attribute is never overwritten and a sem-source fence still shows the markup as written. The hash is &-joined segments (src/shared/state.ts): bare id / container/child deep links, and name=value parameters (sem-audience=<profile>). Every writer edits its own segment only, so #deploy/argocd&sem-audience=operator survives a tab switch. Each element owns exactly the class namespace .sem-<element> and .sem-<element>-*: the alias form's identity class and the element's generated chrome (.sem-facts-chrome, .sem-note-summary, .sem-code-line). No other element may reuse that bare class name for its own chrome. One exception: <incorrect-statement>'s class form is the unprefixed .incorrect-statement, matching its tag name exactly (user decision, v0.7). .sem-progress names only the progress element -- a facts-chrome label needing similar styling is .sem-facts-meter, never .sem-progress borrowed from another element. The npl-* namespace mirrors the rule: each NPL element owns exactly .npl-<element> and .npl-<element>-* -- its class-form identity class (Appendix A, NPL namespace) and its generated chrome (.npl-agent-header, .npl-section-header) -- and no other element may reuse that bare class name for its own chrome.

3. NPL notation inside tags

Compact notation is legal inside element text where the schema allows; attributes are canonical, notation is sugar:

| Notation | Meaning | Where | | :-- | :-- | :-- | | `<highlight>` | recall target -- occludes in quiz/flashcard views, `<em>` in plain view | any prose element | | `[[cloze]]` | inline occlusion sugar (equivalent to `<highlight>`) | `sem-detail`, `sem-fact` | | `term :: value` | pair | `sem-property` text, `sem-fact` compact form | | `? ...` / `? ...` | correct / distractor | `sem-option` sugar | | `- ...` | current | `sem-step` status sugar | | `[hint \| reveal]` | agent-facing instruction, human-rendered hint | instruction-bearing elements (define in `sem-note` schema first) |

<statement>/<conclusion> children always win over :: compact form when both present; authors pick one per fact.

4. The script & degradation rules

One script, always. semtext/semtext.js -- a Lit 3 IIFE, global SemText -- is the format's only script. It defines the interactive custom elements, runs the vanilla handlers for the elements no component defines (sem-views, sem-progress, audience gating, deep-link resolution, print disclosure, the alias mirror, the sem-source snapshot pass), the prose-reading renderers (sem-code chrome, reference / glossary previews, backlinks, the sem-reader chrome, sem-table sort / filter), the Markdown renderer, and extraction -- SemText.extractRecords / SemText.extractText work on the same page that renders, so a document needs no second program to be read by a machine. Every handler selects both authoring forms from one selector (:is(sem-x, .sem-x), the child parts :is(conclusion, .sem-conclusion)) and skips elements the components have already upgraded. The core's first handler snapshots every sem-source wrapper's markup (a DOM clone in an inert template.sem-source-raw child) before any other handler runs; the reading renderers build the fence from that copy. A core handler mirrors each bare tag-form parameter (view-as, variant, name, active, summary, value, label, key) to its data-* twin when the twin is absent, so the gated CSS rules and every later handler read one spelling. The list is exactly the parameters a core handler or a gated CSS rule reads; controls, sticky, lang, filename, mark, wrap, outline-depth, href, cite, implies, when, until, status, kind and tags are read in both spellings by the handler or CSS rule that consumes them and need no mirror. status in particular is never read by a script: its only consumers are the no-script CSS rules of sem-step, sem-event and sem-progress, each written :is([data-status="x"], [status="x"]), which select on a value rather than render an attr() -- both spellings of the same value produce the same declaration, so no :not([data-status]) guard is needed and the alias precedence of §2 cannot be observed unless an element carries two different values, which is the authoring error §2 already names. One runtime, one marker. Components claim data-sem-upgraded at parse time (anti-flash gating needs it); the vanilla handlers -- which stamp the same marker on the elements they wire -- skip elements already claimed, and a component implementation supersedes the same-named vanilla behaviour. semtext.js stamps html with data-sem-upgraded once it has run, for hide rules whose host element is deliberately unmarked (a list-view deck's distractors). The zero-JS elements (sem-procedure, sem-chronology, sem-audiences) and the handler-only ones (sem-views, sem-progress) define no custom element: they are :not(:defined) in every document, by design. The former two-script handoff marker (data-sem-fallback) is removed as of 0.9.0 -- one runtime, one marker. Theme CSS styles both authoring forms from one rule -- :is(sem-x, .sem-x) throughout themes/_vocabulary.css (D10). Rules that must hold with no script read the bare and the data-* spelling ([status="done"], [data-status="done"]; attr(name), attr(data-name)), and a bare-spelling rule is guarded with :not([data-<name>]) so data-* still wins when both are present (§2). Rules that only apply once a tier is driving the element key on the data-* spelling alone, which rule 1 guarantees is present. A tag-form document is therefore presentable before and without any script, with no layout shift on upgrade where feasible. Every hide rule is gated on [data-sem-upgraded] (D12). With no script in the page nothing is hidden and nothing is styled or interactive: incorrect statements render labelled, views stack under their names, collapsed bodies and every conclusion show, audience-qualified content is all visible -- a document without JavaScript shows its authored text, in flow, and is not styled or interactive. dist/demo/*.nojs.html and dist/spec/*.nojs.html are the artifacts that prove it: script-free pages that assert the text is present and unstyled. Content lives in light DOM (searchable, copyable); shadow DOM carries interactive chrome only. Generated chrome is classed (.sem-facts-chrome, .sem-views-tabs, .sem-note-summary) so extraction can skip it; a collapsed note's body is the element's own content, wrapped in .sem-note-body by the code that hides it. Cross-cutting, also in the vocabulary CSS: @media print shows everything a reader could open and no chrome (beforeprint opens reveal disclosures; CSS cannot); prefers-reduced-motion drops transitions and smooth scrolling. Why the budgets are stated raw: a portable single-file document inlines its scripts, and nothing gzips an inlined <script>. The build prints every artifact against its budget; npm run build:strict fails on an overrun, so a budget is raised deliberately in scripts/build.mjs and recorded in the roadmap, never silently.

Document & structure

sem-enhanced-document -- the required root wrapper

Every SemText document wraps its vocabulary in one. Normative statement: §1 Document skeleton -- the script's handlers scope to it, Lit components register against it, and it may carry a role="main" landmark; the alias form may use <main> carrying the sem-enhanced-document class.

sem-reader -- reading chrome: outline, progress, focus, type, colour, print, audience

Normative: spec/schema/sem-reader.md.

<sem-reader controls="outline,progress,focus,type,color,print,audience" outline-depth="3">
  <nav aria-label="Contents">…optional, used verbatim…</nav>
</sem-reader>

One per document, first child of the wrapper. Reading bundle inserts .sem-reader-chrome (role="region"), generates the outline from h2…h<depth> when no nav is authored (aria-current="location" tracks the heading in view), and writes data-sem-mode|type|font and data-color-mode on <html> -- persisted via localStorage, fail-open. Audience writes the sem-audience hash parameter. No global key shortcuts. Mints nothing; extraction skips it whole (extraction §3 rule 7). The theme control is R/W3. The live example is the bar at the top of this page.

sem-audiences / sem-profile -- reader profiles

Metadata, mints nothing. Normative: spec/schema/sem-audiences.md. Active profile = hash sem-audience param, else audience on the root wrapper / data-audience on <html>. The script sets native hidden on non-matching elements; JS-off everything shows; fail-open on unknown tokens.

<sem-audiences>
  <sem-profile id="reader" label="Reader"></sem-profile>
  <sem-profile id="operator" label="Operator" implies="reader"></sem-profile>
</sem-audiences>
<sem-note audience="operator">…</sem-note>
 Operators only: an operator implies reader. Pick a profile from the reading bar's Audience select, or open #sem-audience=operator.

agent -- document-level metadata (bare semantic tag)

Documented in §1 Document skeleton above. Children: <name>, <bio>, <instructions>. Machine-facing, unstyled -- no sem- prefix. Future metadata children (org, context, audience) will follow the same bare-tag pattern.

Prose & code

sem-md -- a Markdown block, rendered in the browser

Normative: spec/schema/sem-md.md.

<sem-md id="m-lifetimes" label="Token lifetimes" controls="toggle,copy">
  | Token   | Lifetime | Rotates |
  | :------ | -------: | :-----: |
  | access  | 15 min   | no      |
  | refresh | 30 days  | yes     |
</sem-md>

The element's text is Markdown (GFM tables, headings, lists, emphasis, links, code, quotes, rules; raw HTML renders as text). The script adds .sem-md-chrome (label, Markdown toggle with aria-pressed, copy, status region), renders into .sem-md-body (real <table> with th[scope="col"], alignment row honoured) and keeps the normalised source in a sem-code fence (.sem-md-raw); view-as="rendered|raw" picks the initial mode and the toggle rewrites data-view-as. JS-off: the source reads as pre-wrapped text. Extraction keeps source normalised (dedented), never the rendering. Every table on this page -- §2, §3, Element buckets, §10, Appendix A -- is this element, with rows identical to the Markdown source.

| Token | Lifetime | Rotates | | :------ | -------: | :-----: | | access | 15 min | no | | refresh | 30 days | yes |

sem-note -- callout

Normative: spec/schema/sem-note.md.

<sem-note variant="warning">Rotation is <strong>per session</strong>.</sem-note>
<sem-note variant="tip" collapsed>Shuffle flashcards before each review session.</sem-note>

variant="info|warning|tip|danger"; the body is the element's content; collapsed ⇒ ten-word teaser, click to expand (the component wraps the body in .sem-note-body to hide it); view-as="margin" ⇒ CSS-only right-gutter aside on wide viewports, inline otherwise. Light DOM, role="note".

Rotation is per session. Shuffle flashcards before each review session for better recall; the deck remembers nothing between sessions.

sem-code -- verbatim listing with provenance and copy / wrap

Normative: spec/schema/sem-code.md.

<sem-code lang="ts" filename="src/rotate.ts" mark="2,4-5" controls="copy,wrap">
<pre><code>…</code></pre>
</sem-code>

Reading bundle adds .sem-code-chrome (filename, lang, buttons, status region), wraps lines (span|mark.sem-code-line, text byte-identical), tabindex="0" on an overflowing <pre>. JS-off: plain <pre> with a CSS caption. Extraction keeps source verbatim.

export function rotate(pair: Pair): Pair {
  const next = mint();
  retire(pair.refresh);
  return next;
}

sem-browser -- chrome-like document window

Normative: spec/schema/sem-browser.md.

<sem-browser src="/demo/example-deck.sem.html" label="the deck">
  <figure class="code-window">
    <div aria-hidden="true">← → ⟳</div>
    <div>demo/example-deck.sem.html</div>
    <iframe src="/demo/example-deck.sem.html" title="the deck" loading="lazy"></iframe>
  </figure>
</sem-browser>

With a src the element fetches the document (parsed with DOMParser, <script> and on* stripped before adoption) into a focusable .sem-window-viewport (role="region"); the authored children are the zero-JS fallback and are hidden once wired. An address bar (.sem-browser-address) shows inert nav glyphs and the declared src as text; the tab title resolves label → the document's <title> → the src basename. Adopted elements are offered to window.SemTextLazy.hydrate, so a lazy-built host renders the deck live. Failures render one role="alert" line; sem-browser-load / sem-browser-error report the outcome. Ships lazy-first (chunks/sem-browser.js) and rides the full bundle after promotion. JS-off: the authored children are the document. No live example here: the element fetches a second document, which a standalone spec page cannot promise.

Disclosure & views

sem-detail / sem-details -- prose with occludable content

Normative: spec/schema/sem-details.md.

<sem-details view-as="quiz">
  <sem-detail>
    The OIDC token travels in the <highlight>Authorization</highlight> header.
  </sem-detail>
</sem-details>

Plain view: <highlight> renders <em>. Quiz view: occluded (▮▮▮), reveal per item, self-check or auto-check.

The OIDC token travels in the Authorization header; refresh tokens never reach the browser.

sem-tag-def / sem-api-call -- reference-definition cards

Normative: spec/schema/sem-tag-def.md, spec/schema/sem-api-call.md. A vocabulary tag's or an API endpoint's contract, authored once, rendered as a card (native table) for readers and extracted as one structured record for machines. sem-tag-def takes tag/name/group/children and one sem-tag-attr row per attribute; sem-api-call takes name/method/endpoint/status and one sem-api-param row per parameter (in = query | header | body | response). Class form mirrors on data-* aliases, like every container above.

sem-reveal -- Q→A disclosure, hidden until the reader acts

Normative: spec/schema/sem-reveal.md.

<sem-reveal summary="Why not localStorage?">
  Tokens in localStorage are readable by any script on the page…
</sem-reveal>

summary optional -- first body line (≤60 chars) derives it, by the one rule in src/shared/summary.ts that render and extraction share; hidden by default, open starts revealed (collapsed accepted, no-op). Tag form: Lit component -- labelled control (aria-expanded) over a blurred body until revealed, one-way. Class form wraps in native <details>/<summary>, closed by default; JS-off: fully visible (summary as small-caps heading). Non-assertive counterpart to sem-fact Q/A shape.

A note is an annotation (variant tone); a reveal is exposition (Q→A). Same mechanism, different semantics -- machines distinguish them.

sem-source -- a section that flips between rendered and authored markup

Normative: spec/schema/sem-source.md.

<sem-source label="Facts -- flashcards">
  <h2>Facts -- flashcards</h2>
  <sem-facts view-as="flashcards">…</sem-facts>
</sem-source>

Chrome Rendered | Source (aria-pressed); view-as="source" starts in source mode, showing the literal markup in a sem-code (copy, wrap) built from the core's pre-enhancement snapshot; the toggle rewrites data-view-as. Transparent to extraction; JS-off: the rendered children, nothing else. Every live example on this page is one; a sem-source never nests inside another, so this entry has no example of its own.

sem-views / sem-view -- same content, switchable perspectives

Normative: spec/schema/sem-views.md.

<sem-views id="deploy">
  <sem-view name="Helm" active role="tabpanel">content…</sem-view>
  <sem-view name="ArgoCD" role="tabpanel">content…</sem-view>
</sem-views>

name unique per container; active marks initial view (first wins if absent; the component keeps the shown view in data-active); it builds the tab bar (.sem-views-tabs, role="tab" buttons), arrow-key roving focus; deep-link #deploy/argocd; fires sem-navigate {id, name, index}. JS-off: all views stacked, name-headed. Q3 resolved v1: sem-views.

Helm renders the chart; the image tag is bumped by CI. ArgoCD auto-syncs from the chart repo's main. Deep link: #x-deploy/argocd.

Facts & recall

sem-facts -- collection; the flagship surface

Normative: spec/schema/sem-facts.md.

<sem-facts view-as="quiz" controls="shuffle,filter">
  <sem-fact>…</sem-fact>
  <sem-fact>…<incorrect-statement>decoy conclusion</incorrect-statement></sem-fact>
</sem-facts>
  • view-as="list" (default): filter box, tag chips.
  • view-as="flashcards": front = statement (+<highlight> prompt), back = conclusion; flip click/Space; ←/→/swipe; progress 3/12; shuffle.
  • view-as="quiz": statement shown; candidates = sibling conclusions, <incorrect-statement> children win when present; accuracy on sem-complete.
  • Events: sem-navigate {index}, sem-flip {face}, sem-complete {correct,total,ms}.
Semantic identity, parameterized presentation sem-fact is a fact in list, flashcard and quiz views -- view-as only changes rendering. What guarantees interactivity? The one semtext.js script. The Tailwind CDN script.

6. Theme conventions

  • data-sem-theme="<slug>" on <html>; one theme per doc; themes compiled from TRP-format YAML → semtext/themes/semtext-theme-<slug>.css; --sem-* tokens; the vocabulary base gives every sem-* element its box before any definition (sem-*:not(:defined) and the never-defined zero-JS elements alike -- custom elements are inline by default, the vocabulary is block-level).
  • Shadow components read tokens via fallback indirection -- zero-JS theme flips.
  • Ship 4 TRP ports: minimal-tech-light (default), nocturne-console, organic-warm, editorial-settings; auto light/dark via prefers-color-scheme, data-color-mode forces.

7. Distribution forms

doc.html + relative semtext/ (IIFE semtext.js + themes/). script + CSS + data all inlined; one file shares anywhere. multi-page bundle. served pages only -- semtext-lazy.js + chunks/ over HTTP(S), and for NPL documents npl-lazy.js + npl-chunks/ the same way (npl.js, the optional full NPL bundle, loads on top of semtext.js instead when no chunk loading is wanted). Each loader imports only the component chunks its document's sem-* / npl-* tags need; core (semtext.js, semtext-lazy.js) carries no npl code. Not portable: dynamic import needs a server, so the page cannot be saved to disk and reopened from file://. Hard rules: no ES-module scripts; no runtime fetch in portable docs; semtext.js is linked (or inlined) in full in every portable form regardless of which of (1)-(3) it takes -- there is no smaller script to fall back to. Form (5), hosted lazy, is the served-pages exception: it swaps the full bundle for on-demand chunks and cannot survive offline.

8. Machine-readability contract

  • Semantic children (<statement>, <conclusion>, <highlight>) + attrs (kind, status, tags, view-as) qualify every datum.
  • Well-formed, correctly nested HTML -- parseable by XML/HTML tooling; the same vocabulary is the XML variant of NPL (§9). Custom elements with bare attributes are what an XML consumer sees: <sem-fact kind="concept"> is one element with one attribute, no class list to tokenise and no data- prefix to strip. The document stays valid HTML5 as well: bare attributes appear only on custom elements, and a standard element carries its qualifier as data-* (§2).
  • Events + attrs documented per schema = agent integration surface.
  • "Text extraction" reference recipe (DOM → annotated plain text) ships with the lib for terminal/LLM pipelines[2].

The extraction invariant (normative)

For any document D, where E is extraction, R(D) is D after semtext.js has run, and I(D) is D after any sequence of user interactions the vocabulary supports (tab switches, card flips, reveals, table sorts and filters, audience profile switches, sem-source / sem-md view toggles, reader chrome changes):

E(D) = E(R(D)) = E(I(R(D)))

Equality is deep equality of the record array, including sourceOrder, and the same guarantee covers every view-as mode. This is the format's central promise: the machine consumer does not get a degraded reading of what the human consumer saw. The full formal statement -- the three refusal rules that make it hold (extraction never looks at generated chrome, runtime state, or presentation attributes: data-view-as, data-active, collapsed) and the one recorded exception (sem-table row reordering, made safe by the data-sem-source-index stamp) -- is normative and lives in spec/extraction.md §5; this section does not weaken or restate it.

What a consumer may rely on

Normative, each item enforced by the tests named below:

  • The record array: flat, document-ordered, sourceOrder = array index, containment a parent index tree; record shape fixed (type, id, kind, tags, audience, parent, fields, text, sourceOrder -- spec/extraction.md §2).
  • audience is carried verbatim on every record and never removes one; filtering by audience is a consumer operation on the extracted array.
  • The annotated plain-text tier (extractText / renderRecordsAsText) is a pure function of the records, so it inherits the invariant unchanged.
  • Extraction itself is a total, pure function: no configuration, no I/O, no DOM mutation (spec/extraction.md §9).

Best-effort only (not guaranteed)

  • Which view an author meant to show first: data-active is a state marker, excluded from extraction by design. An author marks a primary perspective with a durable qualifier (kind, tags) on the view.
  • Live presentation state (quiz answers, current sort, reader font/mode, disclosure state): invisible to extraction. If a consumer needs it, the vocabulary must carry it as a durable qualifier instead.
  • Element families without a schema entry extract as plain records (fields: {}, prose text); their payloads are best-effort until a schema defines them.

Evidence (each bullet is asserted, not aspirational): test/e2e/extraction.cy.js (invariant core: JS-off = JS-on, every view-as, before/after interaction), test/e2e/extraction-reading.cy.js (reading elements; sort + filter deep-equal baseline), test/e2e/sem-table.cy.js (the recorded reordering exception), test/e2e/sem-audiences.cy.js (invariant across profile switches), test/e2e/spec-pages.cy.js (this document itself: records identical JS-off, JS-on, and after interaction).
